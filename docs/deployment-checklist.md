# 部署执行与验收清单

本清单供人工和 AI 共用：先按[部署组合](deployment.md)选择方案，再用对应指南执行，最后逐项验收。命令运行成功只证明该步骤结束，不代表所有选定功能已经可用。

## 1. 明确本次部署范围

开始前确认以下信息；已有部署从现有配置和服务中核对，不重复索要已知信息，也不打印私有配置或凭据。

| 选择 | 需要确定的内容 |
| --- | --- |
| 机器角色 | 工作台节点，或自建中心服务器；中心安装不代替节点安装 |
| 工作区模式 | 部署节点时选 `desktop` 或 `terminal`；已有模式不在线转换，仅部署中心不选工作区模式 |
| 主入口 | 本机 / SSH、CF 单节点、CF 网关，或自建中心；填写自己的域名和节点路径 |
| 端口映射助手 | 需要或不需要；TCP 和串口共用助手。需要时，构建、发布和下载验收均为必做步骤 |
| 其他功能 | 文件中转、屏幕锁、临时账号、WebRTC、TURN、开机运行等，按所选功能验收 |

- 使用普通 Linux 部署用户和可用的 systemd 用户服务；先按[工具说明](node-prerequisites.md)检查 Node / npm、Python、tmux 等依赖。桌面模式需要自己的 Codex CLI；构建助手另需固定 Go 1.26.4。
- 从 Git 克隆源码，保留 `.git` 并确认当前仓库、分支和提交。助手构建使用 Git 提交标识；仅解压源码 ZIP 不足以完成这一步，不伪造版本信息。
- 新部署准备自己的域名、账户、证书或接入授权。CF API Token 默认私有保存于 `secrets/cf_token`（0600）；自建节点接入 key 使用交互隐藏输入，见[凭据对照](access.md#凭据对照)。
- 维护已有实例先核对工作树、部署模式及入口，保留密码、任务、固定助手 v2 key 和规则。只读环境检查用 `npm run deploy -- --check`，它不启动服务，也不验收公网或助手下载。

## 2. 完成所选入口的全部步骤

| 方案 | 执行顺序 | 助手应绑定的最终入口 |
| --- | --- | --- |
| 本机 / SSH | 安装工作台 → 必要时建立 SSH 转发 | 可从助手电脑访问的 localhost 转发地址 |
| CF 单节点 | 安装工作台并配置自己的 Tunnel / 域名 → 验证 HTTPS | 该节点的实际 HTTPS 域名 |
| CF 网关 | 准备网关 → 安装每个节点及独立后端 → `gateway:join` → 验证节点身份和切换 | 固定网关域名及授权节点身份 |
| 自建中心 | 安装中心 → 创建节点授权 → 安装各节点 → `server:join` → `server:doctor` | 完整 `https://desk.example.com/node/node-a/` |
| 接入已有中心 | 直接安装自己的节点 → 领取授权 → `server:join` → `server:doctor` | 管理员分配的完整节点路径 |

详细命令分别见[CF 单节点](cloudflare.md)、[CF 网关](gateway.md)、[中心安装](selfhost-server.md)、[节点接入](selfhost-node.md)。中心命令使用 sudo，节点 npm 命令使用普通用户。不要用作者的域名、Token 或运行状态作为自己的部署配置。

先完成最终入口，后构建助手。还没执行 `gateway:join` / `server:join` 时，不把 localhost、旧独立域名或缺少节点路径的构建当作最终下载包。入口以后变更时重新构建、下载，并复制目标节点的 key。

## 3. 需要助手时完成构建与发布

普通 `npm run deploy` **不构建**助手。选了 TCP / 串口助手时，根据入口当前状态选择一条：

```sh
# 入口已确定，安装或更新工作台并构建四个平台助手
npm run deploy -- --build-forward

# 或：刚完成 gateway:join / server:join，仅按最终入口构建助手
npm run build:forward
```

新 CF 单节点可在自己的完整部署命令上增加 `--build-forward`。首次接入网关 / 自建中心则先完成接入，再构建；构建应在工作台节点仓库执行，不是在只运行中转的中心服务器执行。

- 核对固定 Go 版本和构建退出状态。缺少 Go、构建失败或发布失败时，本项未完成；不要把部署日志里的“助手下载包尚未就绪”当作可以忽略的成功。
- 在**实际节点入口登录**，打开“端口映射 → 下载助手”，确认 Windows x64、Windows ARM64、Mac Apple Silicon、Mac Intel 四项均存在，显示构建版本和 SHA256；按实际使用平台下载并核对。
- 确认包内默认入口和 key 对应最终节点，尤其是自建中心的完整路径。助手电脑必须能访问这个入口；浏览器能打开，或网页外层 Access 已登录，不代表独立助手也已获准访问。
- 在目标电脑启动下载的助手、输入对应槽位 key，核对控制节点、网页在线状态，并验证一条实际需要的 TCP / 串口规则。未拿到目标设备时，分别报告“构建发布已验证”和“目标设备运行未验证”。

后台更新不会替换用户已经下载的程序。助手代码更新后重新下载、启动对应构建；普通 v2 升级不重新生成 key、不删除规则。Mac 首次运行与重置旧格式的例外见[助手说明](forward.md)。

## 4. 部署结束前逐项核对

| 验收项 | 完成标准 |
| --- | --- |
| 工作台节点 | 所选模式和入口服务正常；实际节点 `/readyz` 的 `ok`、`host`、`files` 为 true，节点身份正确 |
| 仅部署中心 | 按[中心验收](selfhost-server.md#验收)检查 HTTPS、首页、`/admin/` 和所选中继能力；这不代表已安装工作台或发布节点助手 |
| 真实入口 | 使用最终域名及完整节点路径，HTTPS 证书正常；自建中心根首页 / `/healthz` 不能代替节点验收 |
| 登录与任务 | 以自己的工作台账号登录；桌面 / 终端可用，重连后原任务保留；粘贴与 Enter 分开，不向工作中的终端注入测试文字 |
| 工作台与文件交接 | 桌面侧栏切换已有任务且输入目标一致；输入面板切换方向保留草稿、清空取回预览；启用文件中转时验证路径复制和加入草稿不自动发送；桌面模式验证共享目录打开及最小化后恢复，见[文件说明](files.md) |
| 助手（已选择时） | 四个平台包已发布、入口和构建正确；目标电脑接入及规则验证结果单独记录 |
| 文件及其他已选功能 | 实测所需的上传下载、权限、节点切换、直连 / 中转或 TURN；直连失败但中转正常时如实说明 |
| 维护交接 | 说明实际入口、模式、所选功能、凭据文件位置、验证范围和未完成项；不输出密码、key 或 Token |

只有全部选定功能完成相应验收后，才报告部署完成。不需要的可选功能标为“不启用”；缺少外部资源、权限或真机条件的项目标为“未完成 / 未验证”，给出具体下一步。`--check` 通过、进程 active、中心显示节点在线、登录页打开、模拟测试通过，都不能单独代替整体验收。

验收表只执行本次角色和功能对应的项目；仅部署中心时，不要求创建未选择的工作台或助手。具体健康地址和测试边界见[验证方法](verification.md#自己部署后的验收)，以后更新见[维护指南](operations.md)。文档修改无需重启服务；已有页面先保存草稿再刷新以加载新界面。
