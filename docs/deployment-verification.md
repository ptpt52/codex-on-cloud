# 部署后自动验收

安装、接入或升级完成后，在对应机器保留的源码仓库中执行。命令读取已保存的部署配置，不使用旧终端继承的域名或模式；不会安装依赖、改配置、启动／重启服务、接管桌面或发送终端输入。

## 工作台节点

桌面与纯终端、独立域名与多节点入口使用同一条命令，以部署用户执行：

```sh
npm run verify:deployment
```

默认不登录。需要验证实际账号及已发布助手时，明确选择：

```sh
npm run verify:deployment -- --login --forward
```

`--login` 从本机私有密码文件读取密码，创建一个验证会话，检查后注销；不解锁屏幕、不接管控制权。它占用账号会话名额，默认检查不创建此会话。登录不自动重试，入口身份未核对通过时不会发送凭据。

需要助手时应显式传 `--forward`，避免“尚未构建”被当作未选择功能。已经发现本机助手发布记录时，即使未传此选项，也会检查现有包。

## 自建中心

中心与节点分别验收。在中心源码仓库使用已安装的固定 Node：

```sh
sudo /opt/codex-selfhost/bootstrap/node/bin/node \
  scripts/verify-deployment.mjs --role center
```

显式验证中心管理员登录时增加 `--login`。默认读取 `/etc/codex-selfhost/server.env`；自定义配置目录使用 `--config-dir /自己的配置目录`。该目录和管理员密码可能需要 root 读取权限。中心不检查节点的助手包，助手验收在每个工作台节点执行。

私有 CA：节点自动沿用已保存的 `SELFHOST_CA_FILE`；也可增加 `--ca-file /path/to/ca.pem` 明确信任证书。中心使用私有证书时同样显式提供 CA。每次 HTTPS 请求保留证书链、有效期和主机名校验，不修改全局信任。

## 自动检查范围

| 检查 | 节点 | 中心 |
| --- | --- | --- |
| 部署配置 | 模式、固定身份、最终域名及完整节点路径、网关／中心配置一致性 | 中心角色、域名与配置一致性 |
| 服务与环境 | 对应模式的用户服务、适用的 Tunnel／frpc；复用 `deploy --check`，含 `native:doctor` 和适用的 WSL 检查；自建节点另复用 `server:doctor` | center、frps、Caddy、coturn 系统服务 |
| 真实入口 | 完整路径的 `/readyz`，核对身份、任务宿主及文件服务 | HTTPS `/healthz`、公开首页、`/admin/` 登录页、匿名节点列表 |
| 界面 | `/ui-version` 与当前仓库生成的界面版本匹配 | 管理子路径可访问 |
| 可选登录 | 节点管理员登录、部署模式及验证会话注销 | 中心管理员登录及验证会话注销 |
| 后台版本（需 `--login`） | 面板、管理、文件服务；桌面模式另核对执行服务 | 中心服务 |
| 助手 | 四个平台包存在，最终入口正确，同一构建、本机完整 SHA256 匹配；选择登录后核对实际入口的四项下载元数据与路径 | 不适用 |

普通 HTTP 仅允许回环地址。本机配置为 HTTPS 时仍检查实际 HTTPS 入口；自建节点使用完整 `/node/<slug>/`。CF 网关检查当前全局默认节点，默认节点不是本机时会报告身份不符，不切换路由。外层 Access 或管理网段白名单阻止命令访问时，从获准环境核对，不自动绕过限制。

源码提交标识只标识本机仓库，**不证明后台进程已加载该提交**。源码未提交、界面匹配、服务 active 和后台代码生效分别报告；后台更新范围按[维护指南](operations.md)核对。

`--login` 会读取实际节点的 `/api/backend-version`，中心则读取 `/admin/api/backend-version`。Node 服务按各自入口的模块依赖和锁文件计算源码摘要，文件服务使用 Python 源码摘要；每个进程在启动时固定摘要、启动时间和 PID，界面热更新不会刷新这些记录。验收将它们与本机源码比较，`deployment.backend` 分组件报告 `match`、`mismatch` 或 `unavailable`。旧服务未提供版本接口时不会记为通过；按维护指南更新对应服务后重新核验，不需要为核验重启原桌面或终端任务。

后台摘要不包含界面专用资源、运行配置、凭据、工作区或助手包；它验证上述服务的启动代码，不能代替真实设备输入、网络拓扑和已下载助手的验收。

助手只要求四项使用同一构建，不要求其提交号等于本轮前端／文档提交。需要锁定特定构建时：

```sh
npm run verify:deployment -- --helper-build 0.9.0+abcdef0 --login
```

将示例值替换为自己实际要求的构建。此选项同时启用 `--forward`。本机哈希与公网元数据匹配，不代表已下载完整公网包或已在目标 Windows／Mac、串口硬件上运行；这些仍在人工项中。

## JSON 与退出码

供 AI 或自动流程读取：

```sh
npm run --silent verify:deployment -- --json
# 明确需要登录与助手时
npm run --silent verify:deployment -- --json --login --forward
```

JSON 含 `version`、`deployment`、`checks` 和 `summary`。每项状态为 `pass`、`fail`、`manual` 或 `skip`；报告不包含密码、Cookie、CSRF、助手 key、代理凭据或终端正文，不自动写入日志文件。

可识别的失败另带固定 `reason`，HTTP 失败带数字 `httpStatus`，区分超时、DNS、证书、错误节点和旧界面；不会复制服务器错误正文。网络失败按本次结果报告，不自动重试。

| 退出码／字段 | 含义 |
| --- | --- |
| `0` | 自动项通过；仍须查看人工项 |
| `1` | 自动检查失败或未完成 |
| `2` | 参数无效 |
| `summary.automatedOk` | 是否没有自动失败项 |
| `summary.manual` | 仍需人工核对的项目数 |
| `summary.acceptanceComplete` | 报告中是否已无失败或人工项；本命令保留实际交互项目，通常为 `false` |

不要只凭退出码 `0` 宣布部署完成。接下来按[共用检查清单](deployment-checklist.md#4-部署结束前逐项核对)验证真实桌面／终端、输入、文件、重连、所选网络路径与目标设备。开发中的模拟测试另见[测试与验证](verification.md)。

## 与其他命令的区别

| 命令 | 用途 |
| --- | --- |
| `npm run deploy -- --check` | 安装前或排障时检查环境，不验收公网和助手 |
| `npm run native:doctor` | 节点本机依赖检查 |
| `npm run server:doctor` | 自建节点的中继、CA、接入与恢复状态 |
| `npm run verify:deployment` | 部署后的综合自动报告，汇总上述适用检查与实际入口结果 |
| `npm test` 等开发规格 | 验证代码，不等于目标部署验收 |

实现限制：最多 64 个检查项；配置最多 64 KiB，密码文件最多 4 KiB、密码本身 16–512 个字符，CA 最多 256 KiB；网络响应最多 512 KiB，每请求最多 6 秒，不跟随重定向；子命令最多 12 秒、输出最多 16 KiB。助手沿用每包 32 MiB、清单 4 KiB 和四平台上限，逐包校验。没有新增持久队列、后台任务或自动重试。

后台版本核算最多 256 个源码文件、每文件 1 MiB、合计 8 MiB；依赖分析在不执行源码的独立解析进程中完成，期限 5 秒、响应最多 128 KiB。诊断接口每次只读固定本机服务，响应及等待时间有界，不改变服务或任务状态。
